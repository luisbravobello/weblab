Tecnología de Internet IISeguridad en el desarrollo web

Hoy aprendes a defender lo que construyes.

Ya sabes hacer sitios que funcionan y se ven bien. Pero una web insegura no es solo un bug: son datos de clientes robados, dinero perdido y la reputación del negocio por el suelo. Hoy ves las amenazas reales, cómo protegerte de cada una y con qué tecnología — incluyendo cómo programar seguro cuando usas IA.

La regla de oro de toda esta clase: nunca confíes en nada que venga del usuario ni en nada que corra en el navegador. Todo lo que el usuario puede tocar, un atacante también. Repite esa frase: es el 80% de la seguridad web.

El plan de hoy // 3 horas

De "funciona" a "está protegido"

Recorremos las amenazas más comunes del desarrollo web. Para cada una verás tres cosas: el ataque (qué pueden hacerte), la defensa (cómo te proteges) y la tecnología (con qué herramienta concreta).

El fundamento // mentalidad de seguridad

Piensa como quien te va a atacar

Antes de técnicas, una forma de pensar. Estos cuatro principios sostienen todo lo demás.

1 · Nunca confíes en la entrada

Todo dato que venga del usuario (formularios, URLs, cabeceras) puede ser malicioso. Valídalo y límpialo siempre, en el servidor.

2 · El cliente es territorio hostil

Todo lo que llega al navegador el usuario lo puede ver y modificar: el HTML, el JS, las variables. Nada secreto vive en el front.

3 · Defensa en capas

No dependas de una sola barrera. Valida en el cliente Y en el servidor, cifra Y limita permisos. Si una falla, otra protege.

4 · Menor privilegio

Cada usuario, cada parte del sistema, solo con los permisos mínimos para su tarea. Si algo se compromete, el daño es limitado.

El error mental #1: "validé el formulario con JavaScript, ya está seguro". No. La validación del cliente es para comodidad del usuario; un atacante salta el navegador y le pega directo a tu servidor. La seguridad real siempre vive en el servidor.

Lo mínimo indispensable // cifrado en tránsito

HTTPS: que nadie espíe en el camino

Sin HTTPS, los datos viajan en texto plano: cualquiera en la misma red Wi-Fi (un café, un aeropuerto) puede leer contraseñas y tarjetas. HTTPS cifra todo entre el navegador y el servidor.

El riesgo

  • Espionaje de la red (man-in-the-middle): leer o alterar lo que viaja.
  • Robo de sesiones y credenciales en redes públicas.
  • Google penaliza en SEO a los sitios sin HTTPS.

Cómo te proteges

  • Instala un certificado TLS/SSL y sirve todo por https://.
  • Redirige todo el tráfico HTTP → HTTPS.
  • Activa HSTS para forzar HTTPS siempre.

Con qué tecnología

  • Let's Encrypt — certificados gratis y automáticos.
  • Cloudflare — HTTPS + protección, plan gratis.
  • Hostings como Netlify/Vercel traen HTTPS incluido.
Dato práctico: hoy no hay excusa para no tener HTTPS — es gratis con Let's Encrypt y automático en la mayoría de hostings modernos. El candado del navegador es lo primero que tus clientes miran para confiar.

El ataque de front-end #1 // Cross-Site Scripting

XSS: cuando el navegador ejecuta código del atacante

Ocurre cuando metes en la página texto del usuario sin limpiarlo. Si un usuario escribe <script> (o una imagen con onerror) en un comentario y tú lo insertas con innerHTML, ese código corre en el navegador de todos los que vean el comentario — y puede robar sesiones, redirigir o alterar la página.

Demo en vivo · pruébalo tú

Un comentario malicioso en un blog

Imagina una caja de comentarios. Abajo está el "comentario" que escribe un atacante. Cambia entre la versión insegura (usa innerHTML) y la segura (usa textContent) y pulsa Publicar. Todo ocurre en un recuadro aislado.

El ataque

El atacante inyecta HTML/JS a través de un campo (comentario, perfil, búsqueda). Si lo muestras con innerHTML, su código se ejecuta en el navegador de tus usuarios.

Cómo te proteges

  • Usa .textContent, no .innerHTML, para texto del usuario.
  • Si necesitas HTML, sanitízalo antes de insertarlo.
  • Activa una CSP (cabecera que bloquea scripts no autorizados).

Con qué tecnología

  • DOMPurify — librería para limpiar HTML.
  • Content-Security-Policy (cabecera HTTP).
  • Frameworks como React escapan por defecto.
comentarios.jsSEGURO
//  PELIGRO: ejecuta lo que sea que el usuario haya escrito
caja.innerHTML = comentario;

//  SEGURO: lo muestra como texto literal, sin ejecutar
caja.textContent = comentario;

//  Si NECESITAS HTML (ej. negritas), límpialo primero:
caja.innerHTML = DOMPurify.sanitize(comentario);

El ataque de back-end #1 // inyección SQL

Inyección SQL: engañar a tu base de datos

Si construyes una consulta a la base de datos pegando texto del usuario, un atacante puede inyectar comandos SQL y saltarse el login, leer toda la base de datos o borrarla. Pruébalo:

Demo · simulación de un login

¿Puedes entrar sin la contraseña?

El ataque

El atacante escribe SQL en un campo de texto. Si lo concatenas en la consulta, ' OR '1'='1 vuelve la condición siempre verdadera y entra sin contraseña.

Cómo te proteges

  • Usa consultas parametrizadas (prepared statements): los datos van por separado, nunca pegados.
  • Valida el tipo y formato de cada campo.
  • Usuario de BD con permisos mínimos.

Con qué tecnología

  • PDO o MySQLi con parámetros (PHP).
  • Un ORM (Eloquent, Prisma, Sequelize).
  • Consultas preparadas en cualquier lenguaje.
login.phpCOMPARA
//  PELIGRO: pega el texto del usuario directo en la consulta
$sql = "SELECT * FROM users WHERE user='" . $_POST['user'] . "'";

//  SEGURO: el dato va como parámetro (?), nunca pegado
$stmt = $pdo->prepare("SELECT * FROM users WHERE user = ?");
$stmt->execute([$_POST['user']]);

Datos que no puedes perder // contraseñas y sesiones

Contraseñas: nunca en texto plano

Si guardas las contraseñas tal cual y te roban la base de datos, el atacante tiene todas las cuentas de tus usuarios — y como la gente reusa contraseñas, también sus correos y bancos. La solución es el hash: una huella irreversible.

miClave123

Quien vea la base de datos la lee tal cual. Inaceptable.

Hash con bcrypt
—

Huella irreversible y única. Aunque roben la BD, no obtienen la clave.

La misma contraseña siempre produce un hash distinto gracias al salt (un valor aleatorio añadido), lo que frena los ataques por tablas precalculadas.

El ataque

  • Robo de la base de datos → todas las cuentas expuestas.
  • Robo de sesión por cookies inseguras.
  • Fuerza bruta sobre el login.

Cómo te proteges

  • Hashea con salt; nunca guardes la clave real.
  • Cookies HttpOnly, Secure, SameSite.
  • Añade MFA/2FA y limita los intentos de login.

Con qué tecnología

  • bcrypt o Argon2 para hashear.
  • En PHP: password_hash() / password_verify().
  • No reinventes el login: Auth0, Firebase Auth, Clerk.
Regla: jamás escribas tu propio algoritmo de cifrado ni tu propio sistema de login desde cero. Usa librerías probadas (password_hash, bcrypt) o un servicio de autenticación. La criptografía casera siempre tiene agujeros.

El error más común de principiante // secretos

API keys y secretos: nunca en el front

Recuerda el principio #2: todo lo que llega al navegador es visible. Si pones tu API key en el JavaScript del front, cualquiera la ve con F12 y la usa a tu nombre (gastando tu cuota o tu dinero). Los secretos viven solo en el servidor.

El ataque

  • Abrir F12 y leer la API key en tu código.
  • Encontrar claves subidas por error a GitHub.
  • Usar tu clave para gastar tu cuota o tu saldo.

Cómo te proteges

  • Guarda los secretos en variables de entorno, no en el código.
  • Las llamadas con clave se hacen desde tu servidor, no desde el front.
  • Pon .env en .gitignore: nunca al repo.

Con qué tecnología

  • Archivos .env + librería dotenv.
  • "Secrets" de Netlify, Vercel, GitHub Actions.
  • Un pequeño backend/proxy que guarde la clave.
.envfuera del repo
# Esto vive en el SERVIDOR y va en .gitignore
API_KEY=sk_live_9f3a...NUNCA_EN_EL_FRONT

# En el código lo lees así, sin exponerlo:
const clave = process.env.API_KEY;
Caso real frecuente: subir una clave a GitHub "por un momentito". Hay bots que escanean GitHub y encuentran claves en segundos. Si pasa: revoca la clave de inmediato — no basta con borrar el commit, ya quedó en el historial.

La capa gratis que casi nadie usa // cabeceras HTTP

Cabeceras de seguridad

Son líneas que tu servidor envía con cada respuesta y que le dicen al navegador cómo protegerse. Son fáciles de activar y suman muchísimo. Enciéndelas y mira qué protege cada una:

Inspector · activa cada cabecera
Enciende las cabeceras para ver tu nivel de protección.
Con qué: en Node/Express se activan casi todas con la librería helmet en una línea. En Apache/Nginx o en Netlify/Vercel se configuran en un archivo de cabeceras. Herramienta para medirte: securityheaders.com.

La puerta de atrás // dependencias y cadena de suministro

Tus dependencias también son riesgo

Tu proyecto usa decenas de paquetes de otros (de npm, Composer…). Si uno tiene una vulnerabilidad —o es malicioso— entra en tu app. El código que no escribiste tú también es tu responsabilidad.

El ataque

  • Un paquete popular tiene un fallo conocido.
  • Un paquete malicioso se disfraza de uno legítimo (typosquatting).
  • Una dependencia pide permisos que no necesita.

Cómo te proteges

  • Revisa vulnerabilidades con npm audit.
  • Mantén las dependencias actualizadas.
  • Instala solo lo necesario, de fuentes confiables.

Con qué tecnología

  • npm audit / composer audit.
  • Dependabot (GitHub) avisa y actualiza solo.
  • Snyk para escaneo continuo.

Lo que define al dev de 2026 // desarrollo seguro con IA

Programar con IA, sin bajar la guardia

La IA (como la que quizá ya usas) acelera muchísimo, pero introduce riesgos nuevos. Usarla bien es una habilidad profesional. Estas son las prácticas que te separan de quien "copia y pega" sin pensar.

Revisa, no copies a ciegas

La IA genera código que puede tener vulnerabilidades (inyección, XSS, validación floja). Entiende cada línea antes de usarla. Si no la entiendes, no la pegues.

Verifica los paquetes

La IA a veces inventa nombres de librerías que no existen. Atacantes registran esos nombres con malware (slopsquatting). Confirma que el paquete existe y es oficial antes de instalarlo.

No pegues secretos en el prompt

Nunca pegues contraseñas, API keys, datos de clientes o código propietario en un chat de IA. Trátalo como algo público.

Cuidado con la inyección de prompts

Si tu app usa IA y le pasa texto del usuario, ese texto puede contener instrucciones maliciosas. Es el "nunca confíes en la entrada" aplicado a la IA.

Pídele que revise seguridad

Úsala a tu favor: "revisa este código buscando vulnerabilidades de seguridad". Pero verifica lo que te diga; es apoyo, no autoridad final.

Licencias y datos

El código generado puede parecerse a código con licencia. Y no entrenes ni subas datos sensibles de tu empresa o clientes a herramientas sin permiso.

La idea que lo une todo: la IA es un copiloto rapidísimo, pero la responsabilidad de que el código sea seguro es tuya. Tienes que saber de seguridad para poder revisar lo que la IA produce — si no, estás metiendo vulnerabilidades a gran velocidad sin saberlo.

Checklist de seguridad para tu proyecto

Antes de publicar cualquier sitio, pásale esta lista. Márcala:

Tu reto para la próxima

  1. Revisa el proyecto de tu negocio y aplícale tres medidas de hoy: HTTPS, que no haya secretos en el front, y validación/escape de cualquier entrada del usuario.
  2. Si usaste IA para algún código, audítalo: ¿hay innerHTML con datos del usuario? ¿consultas pegadas? ¿alguna clave expuesta? Corrige lo que encuentres.
  3. Pasa tu sitio por securityheaders.com y cuéntame qué calificación sacaste y qué cabecera agregarías.
